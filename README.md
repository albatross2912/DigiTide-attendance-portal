# DigiTide — Employee Attendance & Shift Management

A React + Firebase attendance application with server-controlled shift actions, role-based access and a scheduled nightly close.

## Included
- Firebase email/password sign-in
- Employee dashboard with live shift, work and break timers
- Tea, Lunch, Short and Meeting breaks
- End shift (automatically closes an active break)
- Last 14 shifts
- Team Lead live attendance view
- Admin employee creation and role assignment
- Monthly CSV export
- Callable Cloud Functions for all attendance mutations
- Firestore rules deny client writes
- Scheduled close of open shifts at 23:59 Asia/Kolkata

## Requirements
- Node.js 20+
- Firebase project on a plan that supports deploying Cloud Functions and scheduled functions (typically Blaze billing)
- Firebase CLI: `npm install -g firebase-tools`

## 1. Firebase setup
1. Create a Firebase project at https://console.firebase.google.com/
2. Add a Web App and copy its config.
3. Enable Authentication → Sign-in method → Email/Password.
4. Create a Cloud Firestore database.
5. In Project Settings → Your apps, copy the web config into `.env` (copy `.env.example` first).
6. Install and log in to Firebase CLI: `firebase login`.
7. Set this project's ID: `firebase use --add` (or edit `.firebaserc`).

Example `.firebaserc`:
```json
{"projects":{"default":"YOUR_FIREBASE_PROJECT_ID"}}
```

## 2. Install and run frontend
```bash
npm install
cp .env.example .env
# Fill in all VITE_FIREBASE_* values
npm run dev
```
Open the local URL printed by Vite.

## 3. Deploy backend and security rules
```bash
cd functions
npm install
cd ..
firebase deploy --only firestore:rules,functions
```
Scheduled functions require Cloud Scheduler and a billing-enabled Firebase project. Deploying functions may prompt to enable required Google Cloud APIs.

## 4. Create the first admin
Create a user in Firebase Console → Authentication → Add user. Then from the project root:
```bash
npm install --no-save firebase-admin
export GOOGLE_APPLICATION_CREDENTIALS="/secure/path/service-account.json"
node scripts/bootstrap-admin.js admin@company.com
```
Download a service account key only for this trusted setup task. Never put it in `src`, `.env`, Git, or a public hosting provider. Remove the key from the machine when finished. Sign out and sign in again after claims are set so the refreshed token includes `role: admin`.

Admins can then create employee, lead and admin accounts from the Employees section. New accounts receive custom claims automatically.

## Roles
- `employee`: reads own profile, active shift and shift history.
- `lead`: reads all employee profiles, active shifts and shift history.
- `admin`: same read access as lead and can create accounts through a callable function.

Role claims are set by the Admin SDK only. Do not allow client-side role selection or profile writes.

## Data model
- `users/{uid}` — displayName, email, role, department
- `activeShifts/{uid}` — current shift and current break state
- `shifts/{shiftId}` — immutable-ish completed attendance record, userId, timestamps, durations

## Important operational notes
- All timestamps used for official attendance are generated by Cloud Functions using server time.
- Frontend timers are display-only and derive elapsed time from server timestamps.
- Firestore rules deny all browser writes to attendance and user records.
- The nightly scheduled function closes shifts still open at 23:59 India time. This is a safety net, not a substitute for employees ending their shifts.
- This starter treats every Lead as a workspace-wide lead. Add `teamId` and enforce team membership in both queries and Firestore rules if team-only access is required.
- A lead/admin can read all shift records, so use the lead role only for trusted supervisors.
- Monthly CSV export is generated in the browser from records the signed-in lead/admin can read. For very large datasets, move export generation to a paginated callable function.
- Configure Firebase App Check, password reset, MFA and monitoring before production rollout.
- The current frontend uses a temporary password when creating users. For a production deployment, consider an invitation/reset-password flow.
- This source has not been deployed against your Firebase project. Configure Firebase, deploy rules/functions, then test every role and shift transition before using real attendance data.

## DigiTide profile names

The first signed-in user without a saved profile name sees a name setup panel on the dashboard. Saving the name calls the `updateMyProfile` callable Cloud Function, which updates Firebase Authentication and the user's Firestore profile using the Admin SDK. Deploy Functions after installing the updated `functions` dependencies.

For the first administrator, create the user in Firebase Authentication, then run the trusted bootstrap script with a service-account credential on your own machine. You can supply the admin's display name as the second argument. Never put service-account credentials in the frontend or commit them.
